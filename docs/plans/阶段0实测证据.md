## 0A：接收端与麦克风

### 已确认

- Windows 当前存在目标接收端 `VID_1915&PID_1025`。
- PnP 功能包含键盘、鼠标、System Control、Consumer Control、Vendor Defined 和 `SG Control Mic`。
- Raw Input 可枚举 3 个目标设备：Mouse `0x01/0x02`、Keyboard `0x01/0x06`、Consumer `0x0C/0x01`。
- SetupAPI/HID 可枚举 5 个接口；Consumer `0x0C/0x01` 与 System `0x01/0x80` 可只读打开，键盘和鼠标接口因 Windows 输入栈占用而不能直接读。
- `SG Control Mic` 音频端点在线。音频探针只读取峰值，不录音、不保存音频。
- 生产代码已实现直接 HID 与 Raw Input 两条过滤通道；Raw Input 启停硬件烟雾测试通过。
- 真机全通道时序采集已重复得到同一结果：语音键按下产生 `01CF00`，约 `29–37 ms` 后立即回到 `010000`；SH 仍在物理按住约 3–4 秒期间没有持续报告，真正松手时也没有新的 HID 或 Raw Input 事件。
- `SG Control Mic` 的音频由遥控器语音键门控：仅按实体键盘 `Ctrl+Win` 会弹出语音窗口但没有文字；同时按住遥控器语音键并说话后可以正常识别。
- 在微信录音会话已打开时，音量峰值只能证明“正在出现声音”，不能证明“仍在按住”：按住但安静可与松开同为 `0`，松手后缓存峰值又会继续数秒。因此峰值/VAD 不能作为可靠的物理 Release。
- 当前语音键通道已确认是“按下短脉冲”，不是 Push-to-Talk 所需的持续 Down/Release 信号；严格的“按住说、松开立即停”不予放行。
- Vendor Defined 顶层集合为 `UsagePage=0xFF00 / Usage=0x0000`，没有 Input/Output Report，声明了 32 字节 Feature Report；Windows HID 解析器确认只有一个 Feature Value Capability，对应 `Report ID 0x06`。
- 完整解析 Feature Value Capability 后确认：`UsagePage=0xFF00`、`Report ID=0x06`、`BitField=2`、`IsAbsolute=true`、`BitSize=8`、`ReportCount=31`、逻辑范围 `0..255`。32 字节报告由 1 字节 Report ID 加 31 字节不透明厂商数据组成，没有可解释为 Release 的独立 Usage。
- 已按设备声明的唯一 Report ID 调用只读 `HidD_GetFeature`：被动基线读取 225/225 成功、0 错误，返回值固定为 32 字节全零；真机两轮共 524/524 次成功读取。
- Feature 诊断工具没有 `HidD_SetFeature`、`HidD_SetOutputReport`、设备写句柄或未知 Report ID 扫描；不读取普通键盘、不录音。
- Feature 真机动作中，第二轮按下过渡仅有一帧出现 `...00CF00...`，下一次读取立即归零；两轮持续按住和真实松开阶段均为全零。Feature Report 只复现按下短脉冲，不能提供 Release。
- WASAPI 原始包诊断已完成被动基线验证：端点混合格式为 8 kHz、单声道、32-bit Float；持续产生约 10 ms/80 帧的数据包。遥控器松开稳态的数据字节为全零，但 Windows 没有设置 `AUDCLNT_BUFFERFLAGS_SILENT`，因此不能只看静音标志。
- 被动基线启动首包带 `DATA_DISCONTINUITY` 且出现一次非零瞬态，后续归零；正式判定必须忽略捕获流启动预热段，并通过真实静默按住阶段验证麦克风底噪是否稳定非零。
- SH 完成原始包真机诊断后，静默按住两轮的平均 RMS 分别为 `0.00388`、`0.00359`，非零字节比例约 `0.404`；说话阶段平均 RMS 为 `0.02886`。语音相对底噪有明显差异。
- 真实松开后 5 秒内的平均 RMS 分别为 `0.00395`、`0.00343`，非零字节比例仍约 `0.404–0.406`；第一轮松开没有包中断，第二轮虽有 5 次 `DATA_DISCONTINUITY`，但数据未回零且两轮不一致。松开不是音频流的可识别状态变化。
- 第一轮松开后到第二轮按下前，录音流连续保持约 14 秒，麦克风底噪始终存在。结合外部同类 G50S 实测资料“激活模式下持续工作、无需保持按键”，当前接收端更符合“按键唤醒并锁存麦克风”，不是 Push-to-Talk 门控。
- 包级分布中，静默/松开阶段 `RMS >= 0.015` 的最长连续段不超过 3 包（约 30 ms），真实说话阶段为 146 包（约 1.46 秒）。这只证明可以做语音端点实验，不能证明实体松手。
- Windows USB ETW `FullDataBusTrace` 已完成两轮按下、持续按住、实体松手诊断。目标 USB 设备句柄为 `0x1970B8EAE398`，相关中断输入端点为 `0x81/0x82`，音频为 `0x87` 等时端点。
- 第一轮目标中断完成只出现在 `19:12:06.8759812` 与 `19:12:06.8919788`，各 3 字节；实体松手提示为 `19:12:11.1859893`。第二轮目标中断完成只出现在 `19:12:17.7879454` 与 `19:12:17.8279475`，各 3 字节；实体松手提示为 `19:12:21.7810252`。两次松手及其后约 3 秒观察期都没有目标中断完成。
- ETW 的两次 3 字节完成与直接 HID 已确认的 `01CF00 → 010000` 一致。它证明 Release 不是被 Raw Input、HIDClass 或应用程序漏掉，而是当前接收端没有在实体松手时向 USB 主机发送数据。
- USB-IF HID Usage Tables 将 Consumer Page `0xCF` 定义为 `Voice Command`，类型 `OSC`（One Shot Control）。当前短脉冲行为符合一次性“启动语音命令”，不符合持续按键 Down/Up。
- 总线证据保存在 `artifacts/usb-etw-release-20260824-191109/`：ETL 为 `1,441,792` 字节，SHA-256 为 `46C174445BA30BB08A2D9B5D6935A0E87E9A18DD5F9D3DB0E30FED73A55D956A`；诊断没有设备写入、没有保存音频或转写文字。
- 当前电脑的 Bluetooth Support Service 正在运行，但 PnP 枚举没有发现当前存在的 Bluetooth/Bluetooth LE 适配器。因此 BLE 辅助通道若进入原型，需要另接一个 Windows 兼容 USB 蓝牙适配器，或使用第二块 nRF52840 作为 USB 接收端；不能假定本机已有蓝牙硬件。

### 尚未确认

- 替代遥控器/接收端中，哪一款能够同时提供麦克风和真实 Down/Up；商品页不能证明，必须真机验收。
- 当前遥控器的 2.4 GHz 无线包里是否含实体 Release；只有无线侧抓包才能判断，现有 USB 接收端无法回答。
- 当前遥控器内部语音键是独立触点还是矩阵扫描、可用空间、供电电压，以及能否安全接入高阻抗检测或第二微动开关。
- 无线协议的频段、调制、配对、加密和校验方式，以及是否能合理实现自定义接收器。
- `Ctrl+Win` 等目标语音软件快捷键的完整适配矩阵；这项在取得真实 Release 来源后继续。

### 放行步骤

1. 当前 `VID_1915/PID_1025` 已结束 0A 并判为 `OneShotVoice/PushToTalkUnsupported`，不再继续增加应用层轮询或静音猜测。
2. 路线 A：候选替代硬件连续完成至少 20 轮短按、长按和松手；每轮必须有唯一 Down、按住阶段不提前 Up、实体松手时有唯一 Up，同时麦克风有有效语音。
3. 路线 B：先在无线侧分别采集按下、持续按住和松手；只有发现可重复的 Release 差分，才进入协议解析和自定义接收器设计。
4. 任一路线通过后，再让学习器生成 `PhysicalDownUp` 绑定并继续严格 PTT 验收；未通过时不得启用“物理松手提交”。当前硬件可按 SH 已批准的 `VoiceCommandPressAgain` 双按方案运行，但必须明确标为另一种交互。

## 0B：语音软件与快捷键

### 已确认

- 本机存在微信输入法 `2.1.2.13` 相关进程和电脑版微信进程。
- 当前资料显示两者都可能使用 `Ctrl+Win`，因此存在真实冲突风险，不能仅凭快捷键字符串判定归属。
- `RegisterHotKey` 对 F13、Ctrl+Win 和 Ctrl+Win+Shift 的短暂探测均成功；这只说明没有同层 `RegisterHotKey` 占用，不能排除低级键盘钩子、Raw Input 或软件私有监听。
- F13 的真实桌面 `SendInput` Down/Up 批次通过。
- InputGuard 的 Hold、Renew、Release、旧 epoch 拒绝和租约过期自动释放通过；适配器执行层的完整 F13 往返通过。
- 主界面允许编辑触发模型、开始/停止快捷键、进程依赖、冲突进程、禁止修饰键和 VK/ScanCode，不把实现绑定到微信输入法。
- 本机电脑版微信版本为 `4.1.12.55`。在微信输入法与电脑版微信共存状态下，实体键盘长按 `Ctrl+Win` 能弹出语音窗口；同时按住遥控器语音键后可识别并在松开实体 `Ctrl+Win` 时提交到记事本。
- 实体键盘短按 `Ctrl+Win+Shift` 会进入连续语音模式；长按遥控器语音键时能识别并显示候选文字，但松开遥控器 3 秒后仍不提交。第二次短按 `Ctrl+Win+Shift` 后，文字才进入记事本并关闭语音图标。
- 上述结果证明连续模式有可靠的第二次“提交/关闭”动作，但没有证明遥控器松手能产生该动作。

### 尚未确认

- Ctrl+Win 在“仅微信输入法”“仅电脑版微信”“二者共存”三种状态下的真实归属。
- `Ctrl+Win` 与 `Ctrl+Win+Shift` 在微信输入法和电脑版微信共存时的具体归属；当前只确认行为，不把响应方写死。
- `Ctrl+Win`/`Ctrl+Win+Shift` 的 `SendInput` VK/ScanCode 实测；本轮桥接因 HID 脉冲在阈值前结束，尚未执行到注入动作。
- 在记事本、微信和浏览器输入框中的真实文字上屏闭环。
- 第一个可作为默认选项的已验证适配器。因此当前版本不内置伪装成已验证的微信预设。

### 放行步骤

1. 由 SH 手动准备专用测试输入框，并决定是否临时关闭某个第三方软件；项目工具不终止第三方进程、不改第三方快捷键。
2. 在“语音软件”页建立候选适配器，先测试开始快捷键，再测试停止行为。
3. 分别记录隔离态与共存态结果；任何同时响应或归属不明的组合均不得作为默认适配器。
4. 对通过项执行遥控器端到端测试，并确认目标软件结束监听且所有注入键已释放。

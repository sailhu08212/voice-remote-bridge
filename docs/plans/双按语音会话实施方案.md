# 双按语音会话实施方案

> 状态：SH 已于 2026-08-24 批准执行  
> 适用硬件：`VID_1915/PID_1025`、`SG Control Mic`  
> 交互名称：`VoiceCommandPressAgain`（再次按键提交）

## 0. 实施状态

- 状态机、麦克风载波探针、设置项、界面和一次脉冲学习已实现；
- 原有物理 Down/Up 模式保留，二者由明确设置选择；
- 自动化测试和 Debug 构建已通过；
- 真实遥控器短按、长按、第二次提交及异常恢复仍待 SH 在本版本中验收。

因此当前结论是“已实现，待真机验证”，不是“硬件验收通过”。

### 0.1 2026-08-24 卡键实测修订

稳定性测试中，前两轮第二次按键正常停止，第三轮第二次命令未形成停止事件，程序停在 `Speaking`。当时适配器采用 `Ctrl+Win` 的 `HeldAcrossSpeech`，因此 `InputGuard` 按设计继续持有组合键；从用户角度表现为键被卡住。

本次证据说明：一次脉冲硬件不能把“持续持有系统修饰键”作为默认输出。修订如下：

- `VoiceCommandPressAgain` 禁止搭配 `HeldAcrossSpeech/PushToTalk`；当前微信方案改用已经实测可开始/提交的 `Ctrl+Win+Shift`、`Toggle/AtomicBatch`；
- `Speaking` 中仍以第二次 `Pressed` 为正常停止条件；若按下报告丢失，但在启动防抖时间后收到了该脉冲的 `Neutral/Released` 或 `Repeated`，作为同一第二次命令的故障兜底停止；
- 所有页面底部常驻“紧急释放按键”，不再要求先切换到“触发与安全”页；
- 诊断日志记录脱敏后的 `Pressed/Repeated/Neutral/Released`，用于区分“USB 没收到”与“状态机没处理”，仍不记录原始 HID 字节。

切换为 `AtomicBatch` 后，即使第二次命令完全丢失，也只会留下语音窗口等待提交，不会持续按住 Ctrl、Win、Shift 或 Alt；最长会话时限仍负责最终关闭。

### 0.2 开机自启动

稳定性测试 10 轮通过后，增加可选的用户级开机自启动：

- 设置默认关闭，只有 SH 在界面勾选并保存后才启用；
- 使用当前用户的 `HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run`，值名固定为 `VoiceRemoteBridge`，不需要管理员权限，不创建 Windows 服务或计划任务；
- 启用时写入当前实际启动命令并附加 `--background`，兼容自包含 EXE 与开发态 `dotnet + DLL`；软件更新位置后，下次手动运行会按已保存选择校正启动命令；
- Windows 登录启动时主窗口不抢焦点，程序进入托盘并按现有配置启动桥接；双击托盘图标可打开设置；
- 关闭开关后只删除 `VoiceRemoteBridge` 自己的 Run 值，不修改其他启动项；
- 若注册表写入失败，界面显示错误且不把设置保存为“已开启”；设置文件保存失败时回滚启动项，避免界面与 Windows 实际状态不一致。

### 0.3 2026-08-25 输入法自动切换与恢复

SH 已批准为输入法型适配器增加以下可选行为：**语音开始前精确切换到目标输入法，提交完成后恢复本轮开始前的输入法**。当前微信输入法适配器显式启用；其他适配器仍默认关闭，不能把该行为静默扩展到所有语音软件。

实现约束如下：

- 首次长按仍先完成焦点、进程、修饰键、音频端点和麦克风载波检查；短按未激活麦克风时不切换输入法；
- 载波确认后记录当前 TSF 键盘输入配置，再通过 `ITfInputProcessorProfileMgr.ActivateProfile` 按 TIP CLSID、Profile GUID 和语言 ID 精确切换；不得用 `Ctrl+Shift`、`Win+Space` 等循环快捷键猜测目标，也不得调用 `ActivateKeyboardLayout` 冒充现代 TSF 输入法切换；
- 只有再次读取 TSF 活动 Profile 并确认目标已生效后，才进入目标输入法的启动就绪等待，再发送语音开始快捷键；切换、确认或适配器启动失败时不得进入听写，并立即尝试恢复原输入法；
- 启动就绪等待只在本轮确实发生 Profile 切换时执行；已经处于目标输入法时不等待。当前 WeType 初值为 `1000 ms`，用于等待其语音快捷键监听完成初始化；不得用盲目重发 Toggle 快捷键代替等待，因为重发可能关闭已经启动的语音窗口；
- 启动就绪等待结束后再次核对原输入焦点；焦点发生变化时立即恢复原输入法并取消本轮启动，禁止把语音输入发送到其他窗口；
- 第二次按键先发送语音提交快捷键，等待可配置的短暂提交窗口后再恢复原输入法，避免输入法在候选文字写入目标控件前被切走；当前 WeType 初值为 `3000 ms`；
- 正常停止、最长时限、设备断开、程序退出、守护失败和运行异常都必须尝试恢复；紧急路径不等待提交窗口，但仍先停止适配器、释放模拟键，再恢复输入法；
- 如果本轮开始时目标输入法已经激活，则不执行切换，也不在结束时多余恢复；
- 如果恢复失败，必须记录不含转写文字的明确错误并保持按键已释放；恢复失败不能触发重复提交快捷键；
- 该能力只改变当前登录桌面的活动输入 Profile，不修改 Windows 默认输入法列表、默认语言、第三方输入法设置或系统默认麦克风。

当前本机微信输入法精确标识由已安装 TSF 注册信息解析，不硬编码安装目录：TIP CLSID `{86598FB9-66A2-463E-B9C2-AEB906D477AD}`、Profile GUID `{607FDF85-FCC8-4DBD-A365-41296F980C9C}`、语言 ID `0x0804`、说明 `WeType`。运行时以保存的目标名称查找已安装 Profile，并以 GUID 作为最终匹配依据。

#### 0.3.1 WeType Profile 启用授权与边界

2026-08-25 本机实测发现：WeType 注册表 Profile 的 `Enable` 已为 `1`，但不带启用标志的 `ITfInputProcessorProfileMgr.ActivateProfile`、`ITfInputProcessorProfiles.ActivateLanguageProfile` 均返回 `0x80004005`，且 Profile 未进入该进程的 TSF 可激活枚举。SH 随后明确授权执行一次带 `TF_IPPMF_ENABLEPROFILE` 的启用实测。

- 适配器增加 `AllowProfileEnablement` 显式选项，默认关闭；只有当前获批的微信输入法适配器开启；
- 该标志只用于切换到目标 Profile，不得用于恢复原 Profile；
- 目标本来已启用时允许 TSF 幂等确认当前用户的启用状态；不得设置系统默认输入法、默认语言或输入法排序；
- 启用后仍必须再次读取活动 Profile 确认，不能把 API 返回成功直接等同于切换成功；
- 实测结束必须恢复原活动 Profile；启用状态属于安装 Profile 的可用状态，不在每轮结束时禁用。

2026-08-25 交互桌面闭环实测结果：

- 非交互式终端测试进程只能枚举到中文/英文键盘布局，不能枚举微软拼音、WeType 等 TIP；在该环境调用启用或激活返回 `0x80004005`，因此该结果不作为桌面能力结论；
- 从当前登录用户的交互桌面启动同一测试后，原活动 Profile 被识别为微软拼音 `{E7EA138E-69F8-11D7-A6EA-00065B844310}/{E7EA138F-69F8-11D7-A6EA-00065B844311}`；
- 测试按“保存原 Profile → `EnableLanguageProfile(true)` → 带 `TF_IPPMF_ENABLEPROFILE` 激活 WeType → 再次读取确认 → 恢复原 Profile → 再次读取确认”执行，退出码为 `0`；
- 实测发现嵌套创建并释放同一个 TSF COM 对象会使外层 RCW 失效；实现已改为先完成启用调用并释放，再创建独立 Profile Manager 执行激活，两个 COM 生命周期不得重叠；
- 本项只能标记为“TSF 启用/切换/恢复桌面闭环已通过”；遥控器触发、语音提交和焦点保持仍按本文真机验收项单独验证。

#### 0.3.2 WeType 首次切换后的快捷键就绪窗口

2026-08-27 真机测试发现：从其他输入法开始时，第一次长按已完成 WeType Profile 切换，但紧接着发送的 `Ctrl+Win+Shift` 没有弹出语音界面；随后再短按一次，相同快捷键才启动语音界面。该现象按“Profile 已激活，但 WeType 的语音快捷键监听尚未就绪”处理。

- `InputMethodSwitch` 增加 `PostActivationDelayMilliseconds`，允许范围 `0–5000 ms`；
- 等待发生在 TSF 激活确认之后、`StartAdapter` 之前，只对 `Changed=true` 的会话生效；
- 等待可取消；取消、异常或等待后的焦点复核失败都按启动失败处理，并回滚原输入法；
- 停止/提交路径不使用该等待，仍只使用独立的 `RestoreDelayMilliseconds`；
- 当前 WeType 先以 `1000 ms` 进行真机验证，验证目标是“从非 WeType 输入法开始，第一次长按即弹出语音界面”；未通过真机复测前不得标记为已修复。

#### 0.3.3 WeType 启动确认与失败自恢复（SH 已于 2026-08-29 批准实施）

2026-08-29 多屏真机测试发现：程序发送启动快捷键后，即使 WeType 没有弹出语音界面，现有状态机仍会立即进入 `Speaking`。此时下一次遥控器脉冲被误当成“停止/提交”，导致一次失败污染后续尝试；把 ChatGPT 从副屏移回主屏也不会自行恢复。该问题不是简单的屏幕坐标偏移，而是缺少适配器启动结果确认。

为避免采集窗口标题、候选文字或转写内容，使用只记录进程名、窗口类、可见性和矩形的交互桌面观察器进行了两次成功样本采集。两个样本均出现相同信号：

| 样本 | 可见时间 | 进程 / 窗口类 | 窗口矩形 | 结果 |
|---|---|---|---|---|
| 成功样本 1 | `13:04:06.940–13:04:25.810` | `wetype_update / wetype.flutter.setting` | `[585,770,1035,1050]` | 主屏语音界面出现后关闭 |
| 成功样本 2 | `13:04:43.029–13:04:55.325` | `wetype_update / wetype.flutter.setting` | `[3975,770,4425,1050]` | 副屏语音界面出现后关闭 |

因此当前 WeType 适配器可将“指定窗口类进入可见状态”作为启动确认信号。矩形只用于证明主屏和副屏均能被观察，不得把坐标或某一显示器写入匹配条件。

拟实施约束如下：

- 发送启动快捷键后先进入 `Starting`，不得立即进入 `Speaking`；
- 在可配置的确认窗口内，仅匹配适配器声明的进程名和窗口类，并要求窗口可见；当前 WeType 初值拟为 `wetype_update / wetype.flutter.setting`、`2500 ms`；
- 匹配不得读取窗口标题、UI 文本、候选词、转写文字或音频内容，也不得限定屏幕编号和坐标；
- 收到确认后才进入 `Speaking`，第二次遥控器脉冲才具有停止/提交含义；
- 确认超时时，不自动重发 Toggle 快捷键，防止迟到的首次启动被第二次快捷键反向关闭；程序只清除本轮适配器状态、释放全部模拟键、恢复原输入法并回到 `Idle`，同时给出“语音界面未确认启动”的诊断；
- “清除本轮适配器状态”必须有独立的无 Toggle 回滚路径，不得复用正常 `StopAdapter`，否则会把失败恢复变成第二次快捷键注入；
- `Starting` 期间收到新的遥控器脉冲、设备断开、退出、焦点变化或超时，均按启动失败回滚，不得提交；
- 迟到窗口在本轮 epoch 已失效后出现，不得让旧回调把新会话改为 `Speaking`；
- 其他语音软件默认不启用窗口确认；只有完成各自可观测信号验证后，才能在对应适配器中显式配置。

该变更需要调整状态机和适配器执行服务，属于较大行为变更。SH 已于 2026-08-29 明确批准按本节实施。

实现结果：状态机已增加 `Starting`，适配器执行服务已增加不发送停止快捷键的启动回滚，WeType 窗口探针和编辑界面配置已完成；当前配置为 `wetype_update / wetype.flutter.setting / 2500 ms`。Debug/Release 构建、29 项核心测试、Windows 层设置往返与窗口探针测试、发布版 UI 冒烟均通过。主屏/副屏失败自恢复仍须由 SH 使用真实遥控器验收。

#### 0.3.4 单次最长听写时限（SH 已于 2026-08-29 批准调整）

当前运行配置的 `MaximumSpeechSeconds` 为 `120` 秒。到达该时限后，状态机会执行安全停止；它是故障保护，不是 WeType 的语音识别能力上限。若现象稳定发生在约 120 秒并伴随语音界面关闭或提交，则由本软件的安全上限触发；若明显早于 120 秒且语音界面仍在，则应继续检查 WeType 或遥控器麦克风会话。

将 WeType 双按模式的默认值和当前推荐值改为 `300` 秒，仍保留界面可配置及紧急停止能力。超时日志必须明确写出本软件安全时限已触发，避免与第三方识别停止混淆。

实现结果：代码默认值与本机当前配置均已改为 `300` 秒；自动化验证已通过，超过 120 秒的真实语音会话仍待真机验收。

#### 0.3.5 首次短按请求的硬件边界

SH 于 2026-08-29 提出把第一次操作由长按改为短按。现有阶段 0A、音频诊断和真机现象已经一致证明：当前 `SG Control Mic` 只有在遥控器语音键保持按住后才产生持续音频载波，短按后的端点仍为数字零；HID 侧又只有一次性 Voice Command 脉冲，没有可由 Windows 软件利用的实体保持状态或麦克风开启命令。

因此，若仍要求使用遥控器自身麦克风，软件不能把首次短按实现为可用的语音输入。仅跳过载波检查虽然能弹出 WeType 界面，但不会收到遥控器语音，属于不可交付的假功能，本次不实施。

可行边界只有两种：

- 保留首次长按，继续使用遥控器麦克风；
- 新增“首次短按”模式，但语音改由电脑内置麦克风或另一个始终可用的 USB 麦克风采集，并明确不再使用遥控器麦克风。

在 SH 明确选择第二种路径及目标麦克风前，当前正式模式继续保持“首次长按激活遥控器麦克风，再按一次提交”。

#### 0.3.6 多屏及 ChatGPT 兼容中转输入（暂缓，未实施）

2026-08-29 真机复测已排除继续调整等待时间和简单重启第三方进程：

- 将 WeType Profile 切换后的就绪等待从 `1000 ms` 增加到 `2500 ms` 后，副屏普通输入框和副屏 ChatGPT 仍有无法弹出语音界面的情况；
- 退出并重新打开电脑版微信不能恢复；完整重启 `WeType Management Service` 及 `wetype_server`、`wetype_renderer`、`wetype_update` 也不能稳定恢复；
- 同一轮复测中，`14:10:56` 的快捷键发送后确实发生确认超时；`14:11:06` 的下一轮则被现有探针判定为 `wetype_update / wetype.flutter.setting` 可见并进入 `Speaking`，但 SH 在屏幕上仍未看到语音图标；
- 因此 `IsWindowVisible=true` 只能证明 Windows 给窗口设置了可见标志，不能证明它未被 DWM cloak、未透明、未落在可用显示区域、未被遮挡，也不能证明 WeType 已把语音界面绑定到原目标输入框。

随后在完整重启 WeType 并重新升级 ChatGPT 客户端后，SH 复测确认主屏、副屏、微信开启和微信退出四种组合均可正常弹出语音图标并提交文字。由于重启和升级连续发生，现有证据不能把恢复单独归因于其中一个动作，但可以确认当前直接适配路线已经恢复可用。因此本节中转方案暂缓且未实施；保留以下设计只作为未来再次出现不可恢复兼容故障时的备选，不作为当前推荐配置。

备选方案是增加一个由桥接软件自己控制的“兼容中转输入框”，把不稳定的第三方输入控件从 WeType 启动链路中隔离：

```text
保存原输入焦点、原输入法和目标显示器
  → 在目标显示器创建桥接软件自己的标准文本输入窗口
  → 聚焦中转输入框并精确切换、确认 WeType
  → 发送一次开始快捷键
  → 确认语音窗口不仅 Visible，而且未被 DWM cloak、矩形与目标显示器工作区相交
  → 用户说话并再次按遥控器提交
  → 等待 WeType 把文字提交到中转输入框
  → 只在内存中读取本轮文字，立即恢复原窗口、原焦点和原输入法
  → 使用 Unicode 输入把文字写入原输入控件
  → 清空中转输入框和内存缓冲
```

隐私和安全边界：

- 不把中转文字写入文件、日志、诊断页、剪贴板或网络；正常路径优先使用 `SendInput(KEYEVENTF_UNICODE)`，不能静默退化为修改用户剪贴板；
- 日志只记录字符数、阶段、窗口句柄是否仍有效和错误码，不记录文字内容；清理中转框和内存缓冲必须放在成功、取消、超时、断连和异常的共同 `finally` 路径；
- 中转窗口必须显示在原目标输入框所在显示器的工作区内，不得使用负坐标假装隐藏；可以做成小型、明确标注“正在语音输入”的无任务栏工具窗，但不能抢到其他显示器；
- 写回前必须再次确认原窗口和输入控件仍然有效；焦点改变、目标关闭或完整性级别不允许注入时，保留文字只会扩大隐私风险，因此本轮立即清空并提示失败，不自动改投其他窗口；
- 不读取 WeType 候选窗、窗口标题或其他应用文字；只读取桥接软件自己创建的中转输入框；
- 默认禁止剪贴板兜底。若未来发现某类输入控件确实不接受 Unicode 输入，必须把“临时剪贴板写入并恢复”作为单独选项再次取得 SH 授权。

实现前置：该路线会让桥接软件在内存中短暂处理用户转写文字，改变了当前“主程序不接触转写内容”的隐私边界，属于架构变更；必须由 SH 明确批准后才能进入实现。

新增真机验收条件：

1. 主屏和副屏的记事本、Word、浏览器输入框及 ChatGPT 各连续完成 10 轮；
2. WeType 语音窗口必须与中转窗口处于同一目标显示器的可用工作区；系统仅标记 Visible、但 DWM cloak/透明/离屏时不得进入 `Speaking`；
3. 成功提交后原窗口、原输入焦点和原输入法均恢复，文字只进入原目标一次；
4. 启动失败、用户切换窗口、第二次按键过早、设备断开、目标关闭和程序退出均不写错窗口、不遗留文字、不修改剪贴板；
5. 诊断日志和持久化文件扫描不得出现本轮转写内容。

## 1. 目标与能力边界

在不更换、不拆改遥控器的条件下，实现以下交互：

```text
第一次按住语音键
  → 接收端发送一次 Voice Command 脉冲
  → 软件临时打开 SG Control Mic 共享捕获流
  → 确认麦克风已经从数字零进入持续载波
  → 记录原输入法并精确切换、确认微信输入法
  → 等待微信输入法语音快捷键监听就绪，再次核对原输入焦点
  → 启动所选语音软件

第一次实体松手
  → 接收端没有上报 Release
  → 软件保持本轮语音会话

说完后再次轻按语音键
  → 接收端发送第二次 Voice Command 脉冲
  → 软件立即停止适配器并提交文字
  → 等待提交完成窗口后恢复原输入法
```

该模式不是严格 Push-to-Talk。结束依据是第二次真实按下事件，不是第一次松手，也不是静音、VAD、文字稳定或固定时长。

## 2. 为什么第一次可以区分长按与短按

HID 报告本身不能区分长短：两者都会产生相同的 `01CF00 → 010000` 短脉冲。区分依据只能是已经实测的麦克风行为：

- 短按后 `SG Control Mic` 不进入持续活动载波；
- 按住后录音包由数字零变为持续非零底噪，静默按住 RMS 约为 `0.0036–0.0039`；
- 软件只用该信号确认“麦克风已经激活”，不把它用于判断松手或说话结束。

候选初值：

| 参数 | 初值 | 说明 |
|---|---:|---|
| 开始检查延迟 | `150 ms` | 复用现有长按阈值，先过滤机械瞬态 |
| 捕获流预热 | `250 ms` | 忽略 WASAPI 启动首包和不连续瞬态 |
| 激活 RMS | `0.001` | 低于实测静默载波，高于数字零基线 |
| 连续有效包 | `5` | 约 50 ms，避免单包瞬态误判 |
| 激活等待上限 | `1.2 s` | 超时按短按/未激活处理，不弹语音窗口 |
| 语音软件交接重叠 | `500 ms` | 启动适配器后暂时保留探针，避免捕获流切换使麦克风复位 |

以上是当前硬件原型值，必须能在设置模型中调整；未经真机循环测试不能宣称为最终阈值。

## 3. 状态机

```text
Idle
  └─ 第一次 Pressed → Candidate，记录焦点

Candidate
  ├─ 30 ms 后收到 neutral → 忽略为 One Shot 归零，不当作实体松手
  ├─ 到 150 ms → 检查焦点、进程、输入法、修饰键和音频端点
  ├─ 打开共享捕获流，1.2 s 内确认持续载波
  ├─ 保存当前 TSF Profile，切换并确认目标 Profile → 启动就绪等待 → 复核焦点 → StartAdapter → Starting
  └─ 未确认载波/前置检查/切换失败 → 恢复原 Profile → Latched → 冷却后 Idle

Starting（仅启用启动确认的适配器）
  ├─ 确认指定进程/窗口类可见 → Speaking
  └─ 确认超时/新脉冲/断连/退出/焦点变化 → 无 Toggle 回滚 → 恢复原 Profile → Idle

Speaking
  ├─ One Shot neutral → 忽略，继续听写
  ├─ 下一次 Pressed → StopAdapter → 等待提交窗口 → 恢复原 Profile → Stopping
  ├─ 设备断开、程序退出、守护失败 → EmergencyStopAdapter
  └─ 达到安全上限 → StopAdapter

Stopping
  ├─ 适配器确认停止且收到第二次脉冲的 neutral → 冷却后 Idle
  └─ 停止超时 → EmergencyStopAdapter → Latched
```

Listening 状态下第二次只要出现 `Pressed` 就提交，不能等待它的实体松手，因为硬件仍然不会上报实体 Release。

## 4. 适配器兼容方式

双按交互与语音软件适配器解耦：

- `PushToTalk/HeldAcrossSpeech`：只保留给具有可靠连续 Down/Up 的 `PhysicalDownUp` 硬件；一次脉冲双按模式不再允许使用，避免第二次命令丢失时持续占用系统修饰键。
- `Toggle/AtomicBatch`：第一次确认激活后短按一次开始快捷键，第二次按下时再次短按同一快捷键；适合 `Ctrl+Win+Shift` 连续语音模式。
- `StartStopPair`：第一次发送开始组合键，第二次发送独立停止组合键。
- `InputMethodSwitch`：可空的输入法会话策略；包含目标 Profile 名称、切换确认超时、实际切换后的启动就绪等待、提交后恢复延迟和是否恢复。为空时维持原有“仅检查或与输入法无关”行为。

不在运行时把用户选择的适配器偷偷改成另一个快捷键。UI 可以提供推荐配置，但修改第三方快捷键仍由 SH 手动完成。

## 5. 音频隐私与资源管理

- 激活探针只在内存中计算包级 RMS 和非零比例；不保存、回放、上传音频，也不做转写。
- 探针只在 Candidate 和适配器交接窗口打开；完成交接、失败、异常停止、退出或设备断开时必须关闭。
- 探针使用 WASAPI Shared Mode，不改变系统默认麦克风。
- 日志只记录端点名、格式、激活/超时、最大 RMS、连续包数和错误码，不记录样本字节。

## 6. 安全恢复

- `PushToTalk` 适配器继续强制使用 `InputGuard`、epoch 和租约；第二次按键、超时、断连和异常路径都必须释放全部注入键。
- 最大语音时长只作为故障保护，不作为正常提交方式。
- 第二次按键未到时，可通过“停止桥接”、退出程序或诊断页的紧急停止结束；这些路径不得遗留修饰键。
- Candidate 中未确认载波时不得注入任何快捷键。

## 7. 验收

自动化验收：

- One Shot neutral 不会取消 Candidate，也不会停止 Speaking；
- 第一次短按且载波未激活时不产生 `StartAdapter`；
- 载波确认后只产生一次 `StartAdapter`；
- Speaking 中第二次 `Pressed` 只产生一次 `StopAdapter`；
- 重复报告、停止期新按键、过期 epoch、断连和 1000 条变异序列不遗留注入键；
- 音频统计支持当前 8 kHz、单声道、32-bit Float 格式，启动瞬态不会单包放行。
- 目标输入法查找失败、切换调用失败和确认超时都不会发送开始快捷键；
- 实际切换后必须经过启动就绪等待，等待可取消；已经处于目标输入法时不得产生该等待；
- 启动就绪等待后焦点变化时不会发送开始快捷键，并立即尝试恢复原 Profile；
- 已处于目标输入法时不重复切换；正常提交先停止适配器再恢复，异常停止不等待但仍恢复；
- 启动快捷键失败、设备断开、退出和异常路径都尝试恢复原 Profile，且恢复失败不遗留模拟键。
- 启用启动确认时，发送快捷键后停留在 `Starting`；只有匹配窗口可见才进入 `Speaking`；
- 启动确认超时不会重发或发送停止 Toggle，且会清除本轮状态、恢复输入法并回到可再次启动的状态；
- 迟到的窗口确认和过期 epoch 不会污染下一轮；主屏和副屏使用同一进程/窗口类规则，不依赖坐标；
- 单次最长听写触发时记录明确原因，并验证配置值 `300` 秒不会被旧默认值 `120` 秒覆盖。

真机验收：

1. 连续短按 20 次，不弹语音窗口；
2. 长按到“正在听写”后松手并说话，再轻按一次，文字提交；
3. 连续执行 30 轮，开始/提交成功且无 Ctrl/Win/Shift/Alt 卡住；
4. Candidate、Speaking、Stopping 时分别拔出接收端；
5. Speaking 时退出主程序、终止 InputGuard、休眠恢复；
6. 记事本、微信和浏览器输入框分别验收；
7. 分别验证 `Ctrl+Win` 持续按键适配器和 `Ctrl+Win+Shift` Toggle 适配器。
8. 分别从微软拼音、英文键盘和微信输入法开始：前两者在首次长按成功后切到微信输入法，第二次提交后恢复；本来就是微信输入法时全程不发生多余切换。
9. 在 ChatGPT 主屏和副屏分别验证首次启动确认；故意制造一次启动失败后，下一轮无需重启程序即可恢复成功。
10. 连续听写超过 120 秒并在 300 秒内手动提交，确认不会由本软件提前停止。

完成真实硬件验收前，功能状态只能标为“已实现，待真机验证”。
